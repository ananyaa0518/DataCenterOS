# Smart Storage OS Simulator

> An integrated C++ operating-system simulation focused on **storage, memory, process interaction, and I/O performance** in a realistic server environment.

## 📌 Overview

**Smart Storage OS** is a C++-based Operating System simulator that models how a system handles multiple concurrent applications performing file and storage operations.

Instead of implementing individual OS algorithms independently, the project connects multiple OS concepts into a single workflow:

```text
Applications / Processes
          │
          ▼
   Process Management
          │
          ▼
   Context Switching
          │
     ┌────┴─────┐
     ▼          ▼
  Memory      File System
  Manager         │
     │            ▼
     │       Disk Scheduler
     │
     └──────┬─────┘
            ▼
     Synchronization
            │
            ▼
      Storage Device
```

The simulator can model scenarios such as **database reads/writes, log processing, backups, and concurrent file access**.

---

## 🎯 Problem Statement

Modern systems frequently have multiple processes accessing memory and storage simultaneously.

This can lead to:

* Excessive disk-head movement
* Page faults
* Processes waiting for I/O
* Frequent context switches
* Race conditions during concurrent file access
* File-system fragmentation

The goal of this project is to simulate these interactions and provide **performance metrics and bottleneck analysis**.

---

# 🧩 OS Concepts Used

The project combines **five major Operating System concepts**.

### 1. Process Management & Context Switching

Simulate multiple processes and their states:

```text
NEW → READY → RUNNING → WAITING → READY → TERMINATED
```

Each process contains a simplified PCB:

* PID
* Process state
* Program counter
* Registers
* Memory requirements
* File/disk requests

Context switching will simulate saving the current process state and loading another process.

---

### 2. Disk Scheduling

Simulate storage requests generated by processes.

Algorithms:

* FCFS
* SSTF
* SCAN
* C-SCAN
* LOOK

Example:

```text
Initial Head = 53

Requests:
98 183 37 122 14 65

SSTF:

53 → 65 → 37 → 14 → 98 → 122 → 183
```

Metrics:

* Total head movement
* Average seek distance
* Number of requests served
* Average waiting time

---

### 3. Virtual Memory & Paging

Simulate memory allocation using pages and frames.

Features:

* Page tables
* Logical → physical address translation
* Page faults
* FIFO page replacement
* LRU page replacement

Example:

```text
Process P1 requests Page 7

        ↓

Page not present

        ↓

PAGE FAULT

        ↓

Page replacement

        ↓

Page 7 loaded into memory
```

Metrics:

* Page faults
* Page-hit ratio
* Memory utilization
* Number of replacements

---

### 4. Process Synchronization

Simulate multiple processes accessing shared resources such as files.

Implement:

* Mutex
* Semaphores
* Critical sections
* Waiting processes

Example:

```text
P1 → WRITE FILE
P2 → WRITE FILE

P1 acquires lock
P2 waits

P1 completes
Lock released

P2 acquires lock
```

This demonstrates the **critical-section problem** and race-condition prevention.

---

### 5. File System Management

Create a simplified virtual file system.

Features:

* Create file
* Read file
* Write file
* Delete file
* Directory management
* File metadata
* File allocation

Possible allocation strategies:

* Contiguous allocation
* Linked allocation
* Indexed allocation

The file system generates disk I/O requests that are then processed by the disk scheduler.

---

# 🌍 Real-World Use Case

The simulator models a **server/storage environment**.

Example workload:

```text
Database Process
       ↓
    READ DB
       ↓
  Disk Request
       ↓
Disk Scheduler
```

At the same time:

```text
Backup Process → WRITE BACKUP
Log Process    → WRITE LOG
User Process   → READ FILE
```

All processes compete for memory, files, and storage.

The simulator can therefore identify where the system is experiencing bottlenecks.

# 📅 Development Phases

## Phase 1 — Project Foundation

**Goal:** Set up the C++ simulation engine.

Tasks:

* Create repository
* Configure CMake
* Create basic project structure
* Define `Process` and PCB
* Implement process states
* Create simulation engine

### Output

```text
Process Manager
     ↓
Process creation
     ↓
State transitions
```

---

## Phase 2 — Context Switching

**Goal:** Simulate process switching.

Tasks:

* Implement process context
* Simulate registers/program counter
* Save process state
* Restore process state
* Track context-switch count
* Generate process execution logs

### Output

```text
P1 RUNNING
     ↓
P1 WAITING
     ↓
Context Switch
     ↓
P2 RUNNING
```

---

## Phase 3 — Virtual Memory

**Goal:** Add memory management.

Tasks:

* Implement pages and frames
* Create page table
* Address translation
* Page-fault handling
* FIFO replacement
* LRU replacement

### Metrics

```text
Page Faults
Page Hits
Hit Ratio
Memory Utilization
```

---

## Phase 4 — File System

**Goal:** Create a virtual file system.

Tasks:

* File creation
* Read/write operations
* Delete operations
* Directory structure
* File metadata
* File allocation

Every file operation should generate appropriate storage requests.

---

## Phase 5 — Disk Scheduling

**Goal:** Optimize storage requests.

Implement:

```text
FCFS
SSTF
SCAN
C-SCAN
LOOK
```

Compare:

```text
Total Head Movement
Average Seek Distance
Requests Served
```

The disk scheduler receives requests generated by the **file system and processes**, making this module part of the larger simulation.

---

## Phase 6 — Synchronization

**Goal:** Handle concurrent file access.

Implement:

* Mutex
* Semaphore
* Critical sections
* Process waiting

Example:

```text
P1 → WRITE
P2 → WRITE

      ↓

Synchronization Manager

      ↓

Only one process enters
the critical section.
```

---

## Phase 7 — Integration

**Goal:** Connect all OS components.

Example workflow:

```text
Process Created
      ↓
Memory Allocated
      ↓
Process Runs
      ↓
File Requested
      ↓
Synchronization Check
      ↓
Disk Request Generated
      ↓
Process Waits
      ↓
Context Switch
      ↓
Disk Request Completed
      ↓
Process Resumes
```

This is the point where the project becomes an **integrated OS simulator rather than separate algorithm implementations**.

# 🚀 Final Goal

The final system should allow a user to create a workload such as:

```text
12 Processes
50 File Operations
30 Disk Requests
100 Page Requests
Multiple Concurrent File Accesses
```

and then simulate the complete lifecycle:

```text
        PROCESS
           ↓
   MEMORY ALLOCATION
           ↓
       EXECUTION
           ↓
     FILE OPERATION
           ↓
    SYNCHRONIZATION
           ↓
      DISK REQUEST
           ↓
    DISK SCHEDULING
           ↓
    I/O COMPLETION
           ↓
   CONTEXT SWITCH
           ↓
      PROCESS RESUMES
```

The final output is a **performance report and optional interactive dashboard** showing how the different OS mechanisms affected the workload.
